# Native bounded BM25 candidate walks and data-read ceilings

## Scope, deliberately not activation

This extends the private complete-tuple/query foundations with an ordinary-library BM25 **method-candidate** walk, distinct-file rank reduction, typed cached-original unavailability, and aggregate data-read enforcement. It does not activate the application, replace its resident compatibility path, complete the all-method Query controller, qualify final transport/delivery ownership, or establish M4–M6/full-product READY. Native macOS, installed workflows, loaded WeMM/quality/multimodal and physical full-product M0 acceptance remain separate.

Canonical requirements remain in [search](../specs/search.md), [service](../specs/service.md), and [test strategy](../specs/test-strategy.md).

## Existing owners and engines

`NativeTupleQuery::bm25_requirement` streams already-paid metadata to conservatively quote the actual current-shard peak, bounded winning-source/page tails, scalar-result copies, existing 128 MiB kernel work and existing range-reader quote. The quote is data, not a grant. `start_bm25` requires the actual matching Claim and the exact admitted BM25 keyword/library.

`NativeBm25Run` advances actual sealed catalog/source frames and actual M1 read pages. Fresh SDK source scopes are split from the **same** Claim before retained copies/original-FD inspection. The actual tuple/root/model/SDK intention, source UUID/path/version, original FD, cancellation, budget and original deadlines remain checked. Typed missing/changed originals are distinguished from global policy/Claim/cache failures and **owning** setup refusals; the latter are never converted into omitted rows.

Every native partition reuses the SAME `SourceGeneration`, eligible-only mature Tantivy statistics/analyzers and `HeldRangeReaders`. Kernel/range work returns only after actual generation/result/byte consumers die. Winning original scopes, page pins and prepaid output copies survive through their actual consumers. Unpinned old pages are collected without retaining a corpus-sized FD/page set. Failed steps are terminal, keep their actual owner, and cannot retry effects. Cleanup returns that owner if a real SDK/page/range consumer still exists. A typed budget context preserves, rather than discards, any underlying owning refusal.

These are candidate primitives. In particular, final composite all-method dependency/exposure/delivery checks must not be inferred merely from the walk's EOF or from a detached hit DTO.

Administrative data also needs its actual tail. A separate real `query-drop-tail` control allocates an 8 KiB owned error buffer under the actual run's administrative loan, then observes the real Core account while that buffer is still live during destruction under full memory/storage pressure. OLD field destruction order released **397056 bytes** first; the control actually failed. Declaring paid data before its funding field makes Rust destroy data first: the restored control observes **zero** available bytes until the buffer dies. No custom cleanup engine, fake backend, resource limit increase or static quarantine is involved. The failure control settles its actual synchronous job before reporting the assertion. Caller drop is not evidence of unknown process/group/IO settlement, and normal explicit same-Claim finish/rejoin remains required. The added twelfth corpus mode does not replace any existing successful or hostile mode.

## One original, one method/keyword contribution

`knowledge-search::FileRankWindow` retains only the requested number of distinct originals for one method/keyword/library. Each file keeps its **best partition rank**; logical path/source ID give stable ties. Raw independent-partition BM25 scores are not compared. The resulting ordered file list is supplied once to existing mature method/keyword RRF; the mature text scorer and RRF function are not replaced. Partition identity remains qualified by the actual generation/scope; independent libraries are not presented as one statistical corpus.

Keeping all partition lists is corpus-sized. Feeding every fragment partition directly to RRF gives a long original extra votes. The real additional `ranking` fixture uses the actual M1→M3→tuple→native query path, a long original at least as large as the existing high-frequency fixture, ten actual partitions, and an earlier-path single short original. Test-only direct partition-list fusion through the **existing** RRF actually fails the file-order control; restoring bounded best-rank reduction passes. The original high-frequency hostile datasets remain unchanged in all their existing modes. This is not a retrieval-quality/WeMM benchmark or a claim of one global statistical corpus across independent partitions.

## Data ceilings are not another resource account

`ReadAllowance` restricts data reads within actual already-paid scope/Claim resources. It creates no Core account, queue, source grant, memory promise or permission cache. Framed metadata is charged **before** prefix/body reads and allocation; the same actual host admission runs before immutable range refill allocation/IO. Every existing currentness/permission check remains independent.

The existing synchronous M1 decoder has its own actual byte bound. Its full possible data span is held against the same allowance while it runs, excluding competing refills. Only the unconsumed **data** span is returned after successful known decoder completion/native read spend. Errors keep a conservative spend; Core holdings are neither refunded nor re-reserved by this counter. Reported admitted bytes are not measured RSS or invented completed-IO totals.

Pre-submission input work is separately funded and obeys the sealed request. An immutable data baseline is recorded at actual aggregate submission; the effective read limit is `min(sealed request limit, input baseline + actual Claim execution limit)`. This is not cached authority. Unclaimed quote IO is disallowed after submission. An actual 22 MiB execution control caught the overguard from incorrectly charging prior input work against execution again; the restored control succeeds without raising its bound.

The actual one-byte Claim control first failed because cached metadata was read before admission. The repaired path refuses before additional metadata/index payload reads, reports a typed budget refusal rather than source absence, and returns actual loans. A separate actual 20 MiB execution control reaches native range IO and refuses before an over-budget result. Test-only removal of range admission actually completes incorrectly and fails that control. Neither underlying request ceilings nor time limits were raised.

## Necessary existing M1 buffered-read repair

A logical journal cursor is not native IO admission. On Linux, a real one-byte readonly M1 call previously read **3317 native bytes** through buffered read-ahead while reporting cursor zero. The existing journal/parser now places standard `std::io::Take` **below** its existing `BufReader`, bounds resumed predecessor inspection before allocation/read, and exposes native read spend including buffering. There is no new filesystem/backend/replay engine or writable impersonation.

The native control measures actual owning-thread kernel IO, including a resumed EOF/predecessor case; it subtracts only its own `/proc/thread-self/io` snapshot read. One-byte and resumed controls now stay within their actual ceilings without journal/tree mutation or a writer grant. Existing portable read-owner/continuity checks remain. Linux kernel-counter success is not macOS physical acceptance.

Earlier public native CI qualifies only its earlier exact public tree, never these private changes.
